# NFL Pool Standings — Design

## Purpose

A static-site score calculator for a "pick your teams" NFL pool: each
participant ("better") picks a set of NFL teams; a team scores
`wins − divisional losses`; a better's score is the sum across their
picks. The output is a single `index.html` with a sortable leaderboard
and team table, hosted for free on GitHub Pages with no always-on
server. This replaces a prior Rust implementation
(`CRGA_Football`, RapidAPI-backed) with a Python implementation backed
by ESPN's public API, following the fetch/parse patterns used in
`faults-and-fortunes`.

## Data source

ESPN's site API returns everything needed for scoring in a single
request:

```
GET https://site.api.espn.com/apis/v2/sports/football/nfl/standings?season={year}
```

Each team's `stats` array includes `wins`, `losses`, `divisionWins`,
`divisionLosses` directly — no need to replay the season's
game-by-game results to compute divisional losses (the approach the
old Rust project used). Team metadata (`displayName`, logo href) is
included on the same entry.

ESPN 403s a bare/empty User-Agent; requests must set a generic UA
(e.g. `curl/8.5.0`, matching `faults-and-fortunes`'s `EspnProvider`).

ESPN sends no CORS headers on this endpoint, so a client-side
(browser) fetch from a statically-hosted page will not work reliably —
`index.html` must be generated by a script, not built dynamically in
the browser.

## Components

All under `src/gridiron/`:

- **`espn.py`** — `fetch_standings(season: int) -> dict[str, Team]`.
  Issues the HTTP request, parses the JSON, returns a dict keyed by
  the team's full display name (e.g. `"Buffalo Bills"`) matching the
  names used in `picks.txt`.

  ```python
  @dataclass
  class Team:
      name: str
      wins: int
      losses: int
      division_wins: int
      division_losses: int
      logo_url: str

      def score(self) -> int:
          return self.wins - self.division_losses
  ```

- **`picks.py`** — `parse_picks(text: str) -> list[Better]`. Same
  format as the old `better_picks.txt`: a better's name on one line,
  followed by one picked team name per line, blocks separated by a
  blank line. Picks file lives at repo root as `picks.txt`, one per
  pool/season, hand-edited at draft time.

  ```python
  @dataclass
  class Better:
      name: str
      picks: list[str]
  ```

- **`scoring.py`** — pure functions operating on `Better` +
  `dict[str, Team]`:
  - `better_score(better, teams) -> int`
  - `better_wins(better, teams) -> int`
  - `better_losses(better, teams) -> int`
  - `better_division_losses(better, teams) -> int`
  - `better_games_played(better, teams) -> int`

  A pick name with no matching entry in `teams` raises a `KeyError`
  with a message naming the better and the unmatched team — this must
  surface as a failed run (bad picks.txt entry), never a silently
  dropped pick.

- **`render.py`** — Jinja2 template (`templates/index.html.j2`) →
  `index.html` string. Reuses the two-table UI from `CRGA_Football`
  (leaderboard: better/score/wins/losses/div-losses/games-played,
  sortable by clicking headers, search box; teams table: logo,
  score/wins/losses/div-losses/games-played, which betters picked
  each team, click-a-better-name to filter). Same vanilla-JS
  sort/filter, no framework, no build step, no external assets besides
  ESPN's own logo CDN URLs.

- **`main.py`** — CLI entry point (`gridiron` script, per
  `pyproject.toml`). Steps: read `picks.txt` → `fetch_standings` for
  the current season → score → render → write `index.html` to repo
  root. Season year: defaults to the current calendar year, override
  via `--season`.

## Error handling

- Bad/missing pick name → `KeyError`, non-zero exit, no `index.html`
  written. (Fail fast, matches the old project's `.unwrap()` behavior,
  but with a message that names the offending pick instead of a raw
  panic.)
- ESPN request failure (non-200, timeout, malformed JSON) → exception
  propagates, non-zero exit, no `index.html` written.
- Both cases: the GitHub Action run fails and no commit happens, so a
  transient ESPN outage or a draft-day typo never overwrites a working
  page with broken output.

## Testing

- `tests/test_espn.py` — parses a saved fixture standings JSON
  (`tests/fixtures/standings.json`, a trimmed real response) into
  `Team` objects; asserts wins/losses/division fields and `score()`.
- `tests/test_picks.py` — parses a small fixture `picks.txt` block
  into `Better` objects.
- `tests/test_scoring.py` — combines fixture `Better`s and `Team`s,
  asserts the four scoring functions.
- `tests/test_render.py` — renders with fixture data, asserts the
  output contains expected rows (spot checks, not full-HTML
  snapshotting).
- No live network calls in the test suite.

## Automation (GitHub Actions)

`.github/workflows/update-standings.yml`:

- Triggers: `schedule` — daily during the NFL season (cron, e.g. `0
  11 * * 2` — Tuesday mornings UTC, after Monday Night Football) —
  plus `workflow_dispatch` for a manual run.
- Steps: checkout, install `uv`, `uv run gridiron`, then commit
  `index.html` only if it changed, push to `main`.
- GitHub Pages serves directly from `main` (root), so a successful
  push is the entire deploy.

## Documentation

`README.md` covers:

- What the pool is and how scoring works.
- How to edit `picks.txt` for a new season/draft.
- How to run the generator locally (`uv run gridiron`).
- How to enable GitHub Pages for this repo (Settings → Pages → Deploy
  from branch → `main` / root).
- How to point a custom domain at GitHub Pages: adding a `CNAME` file
  to the repo, and the DNS records to create — `A`/`ALIAS`/`ANAME`
  records at the registrar for an apex domain (GitHub Pages' four IPs),
  or a `CNAME` record for a subdomain (e.g. `standings.example.com` →
  `<user>.github.io`).

## Out of scope

- Multiple simultaneous pools/seasons in one deployment.
- A UI for editing picks (still a hand-edited text file).
- Live/in-game score updates (standings only reflect completed games
  as ESPN reports them; no play-by-play).
